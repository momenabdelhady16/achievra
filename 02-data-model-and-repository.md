# 02 — Data Model & Repository Specification

## 1. Task record

```typescript
interface Todo {
  id: string;                 // Immutable; generated by the repository
  title: string;              // Normalized, 1–32 grapheme clusters
  description: string;        // Normalized, 0–256 grapheme clusters; default ""
  dueDates: string[];            // Unique YYYY-MM-DD due dates; [] means undated
  completed: boolean;         // Explicit Boolean status
  completedAt: string | null; // UTC ISO-8601 instant set on completion; null while pending
}
```

`id` is never accepted from user input and cannot be changed by update. The repository creates it during `create()` and returns the saved `Todo`. The LocalStorage adapter may use `crypto.randomUUID()`; another adapter may use a database-generated key while fulfilling the same contract. The service is not coupled to either strategy.

`title` must not be empty after normalization. `description` may be empty and is displayed as “No description”. `dueDates` may contain zero, one, or several distinct valid calendar dates. Removing a date from a multi-date Pending task removes only that date; removing its final date leaves `dueDates: []`. Completed tasks cannot be edited, including removal of their due dates. A task with several dates is still one task and one card. `completedAt` is internal metadata, not user-editable input; it is assigned as a UTC ISO-8601 instant when a pending task is marked complete. Due-date comparisons remain date-only and do not use this timestamp.

## 2. Text normalization and counting

Before validation, duplicate comparison, and persistence, normalize each user-entered title/description independently:
1. Trim leading and trailing whitespace.
2. Collapse each run of internal whitespace (including tabs/newlines) to one space within the entered value.
3. Reject a normalized blank title.

When descriptions are merged, if the old description is non-empty, join the normalized old and new descriptions with exactly one newline. If the old description is empty, store the normalized new description without a leading newline. Do not run whitespace normalization over the combined merged value afterward. Count any stored newline as one grapheme for the 256-character combined limit.

Count user-perceived Unicode grapheme clusters, so each visible symbol counts as one character whether Arabic, English, punctuation, digits, or emoji. Do not count UTF-16 code units. Apply this rule to title/description validation and live counters. Use `Intl.Segmenter` with `granularity: "grapheme"` or an equivalent grapheme-segmentation implementation; `Array.from()` alone is not sufficient for joined emoji. Limits: title 32; description 256. UI counters show current count and limit (for example `12 / 32`).

## 3. Date representation and comparison

Dates are calendar dates in `YYYY-MM-DD`; they have no time-of-day or timezone component. Determine “today” from the current calendar year, month, and day only. Timezone conversions must not move a date to the previous or next day. Validate actual calendar dates, not only the shape of the string. Ordering/comparison uses date components/calendar day only.

## 4. LocalStorage envelope and migration

Use one key (default `todos_app_data`) and a versioned envelope:
```json
{
  "schemaVersion": 2,
  "todos": [
    {
      "id": "example-id",
      "title": "Buy groceries",
      "description": "Milk and eggs",
      "dueDates": ["2026-10-25", "2026-11-05"],
      "completed": false,
      "completedAt": null
    }
  ]
}
```

Version 2 migration must preserve every valid version 1 task:
- Convert old `date: null` to `dueDates: []`; convert a valid old `date` string to `dueDates: [date]`.
- Preserve `id`, `title`, `description`, and `completed`.
- Set `completedAt: null` for old completed records because version 1 contains no completion timestamp. Their relative historical completion times cannot be reconstructed; preserve their stored array order as legacy order and place this legacy group before tasks completed after migration. Pending legacy records retain `completedAt: null` until completion.
- Validate the migrated envelope before writing the new version. Never discard valid task content during migration. Unknown versions or invalid records are not auto-overwritten.

For every write, read/validate the current envelope, form the complete next envelope, serialize it, then call `localStorage.setItem`. The DOM must not reflect a create/update/delete until the repository operation succeeds. Handle LocalStorage access and quota failures as storage failures.

## 5. Asynchronous repository contract

Every adapter implements the same asynchronous contract and returns copies, not mutable internal references:

```javascript
class TodoRepository {
  async getAll() {}                         // Promise<Todo[]>
  async create(todoData, options?) {}        // Promise<Todo> with repository-generated id
  async update(id, changes, options?) {}     // Promise<Todo>; id is immutable
  async merge(sourceId, targetId, targetChanges, options?) {} // Promise<Todo>; atomically persist target update and source removal
  async deleteMany(ids, options?) {}         // Promise<{ deletedIds: string[], failures: Array<{ id: string, message: string }> }>
  async restoreTodoSnapshot(todoSnapshot, options?) {} // Promise<Todo>; journal recovery only
}
```

`getAll()` returns `Todo[]`. `create()` receives title, description, dueDates, and completion status/metadata as appropriate (never an ID). `update()` receives an ID plus allowed changed fields. `merge()` receives source and target IDs plus the target's resulting fields. `deleteMany()` receives IDs and reports each deletion that failed. Single-record operations reject with a typed validation/storage error; batch operations include per-record failure messages so the UI can identify the affected item and explain the failure.

`create(todoData)` accepts domain fields other than `id`; the repository assigns the identifier, persists, and returns the saved record. `update(id, changes)` accepts only editable domain fields, cannot change `id`, rejects missing records and invalid changes, and returns the persisted task. `merge(sourceId, targetId, targetChanges)` atomically saves the merged target and removes the absorbed source, returning the saved target; on failure neither record may be partially changed. This operation is needed for the agreed edit-into-existing-task workflow. The optional `options.beforePersist` callback receives complete before/after snapshots after ID generation and validation but before the task envelope is written; the adapter must await it, and must not persist if it rejects. `options.operationType` and `options.metadata` describe repository-level recovery or merge context. `restoreTodoSnapshot` is restricted to trusted, validated journal recovery and preserves the supplied repository-generated ID. These operations are asynchronous even when LocalStorage itself is synchronous. Batch deletion may partially succeed; its result identifies successful IDs and per-ID failures, including a user-displayable reason. The service depends only on this contract, not LocalStorage, HTTP, SQL, or database details. No speculative search/category methods are required in the MVP.

## 6. Write-ahead operation journal

The operation journal is stored separately from the Todo envelope under `achievra_todo_operation_log`, with envelope shape `{ schemaVersion: 1, entries: TodoOperationLogEntry[] }`. `LocalStorageTodoOperationLogRepository` implements the independent `TodoOperationLogRepository` contract; task records and log entries must never share one mutable envelope.

The repository assigns a create ID, validates and constructs the complete proposed Todo, then invokes the injected pre-persist hook. That hook appends the journal entry before the Todo adapter writes the Todo envelope. For updates, completion, merge, recovery writes, and delete commits, the adapter similarly supplies the complete before/after snapshots to the hook before writing. If recording the intent fails, the Todo mutation must not be written.

Every `TodoOperationLogEntry` records:

- `operationId`, `operationType` (`create`, `update`, `merge`, `complete`, `delete`, or `recovery`), `status`, `taskId`, all `relatedTaskIds`, `requestedAt`, `updatedAt`, and optional `deleteDeadlineAt`.
- Complete `before` and intended `after` Todo snapshots, including IDs, title, description, every due date, `completed`, and `completedAt`.
- `metadata.source`, validation result/time (including `null` when validation could not be reached), before/after/persisted task summaries, changed field names per ID, and text/date/status metadata for every snapshot. Title and description lengths use the same grapheme counter as the UI and validation; both record their maximum and remaining allowed characters, and descriptions also record whether they are empty.
- Persistence state and timestamps, explicit `{ completed, resultStatus }` outcome, failure category (`validation`, `storage`, or `unknown`), error name, field, and message.
- UI check state/time, recovery-required state, attempt count, last attempt/outcome, and whether user action is needed. Delete entries additionally record request time, the five-second grace duration, commit request time, and undo time.
- Non-persisted duplicate and confirmation-required create/update/merge results are also logged with their proposed normalized fields, matched task snapshot/ID when one exists, result reason/message, and an explicit `completed: false` outcome. They are final journal outcomes and are never replayed as pending writes.
- Validation-rejected create/update attempts retain the proposed title, description, their character counts, due dates, failed field, and reason, even though no task ID or storage write exists yet. Failures before the write-ahead callback retain all available proposed input and task ID, classify validation as failed or not yet reached, and record the failure category and reason.

Entry lifecycle states are `prepared`, `delete-pending`, `commit-requested`, `committed`, `failed`, `undone`, `needs-user-input`, `duplicate`, and `confirmation-required`. A failed or interrupted entry is not discarded. On startup, the composition root compares unresolved entries by task ID with persisted Todo data. If the intended after-state is already present, it marks the entry committed. If the before-state is still present and the after snapshot is complete and valid, it replays the exact intended mutation, preserving the repository-generated ID. An unresolved `delete-pending` or `commit-requested` delete resumes with a fresh five-second undo interval while the Todo stays stored. A delete explicitly marked `failed` is retained in the journal but is not automatically retried; the saved Todo loads normally. If neither snapshot matches or required data is incomplete, it preserves available fields in the task form, explains the interruption, and requests user review. Duplicate and confirmation-required outcomes are final and are not replayed. A corrupt/unsupported journal is not overwritten or cleared automatically.

Every five seconds while visible, a separate checker examines only entries updated during the preceding seven seconds and verifies each affected task ID against storage and its rendered card. It repairs only affected IDs. A per-task deletion grace record remains unresolved until explicitly undone or deletion commits.

## 7. Operation-log repository contract

| Method | Contract role |
|---|---|
| `getAll()` | Read and validate detached operation-entry copies. |
| `append(entry)` | Append a unique, fully populated write-ahead entry before task persistence. |
| `update(operationId, changes)` | Update lifecycle state and outcome metadata without removing the entry. |

The operation-log service is storage-independent and depends only on this contract. A future database migration can replace both storage adapters while retaining the journal schema and Todo domain rules.

## 8. Failure types and user-visible behavior

Keep validation failures distinct from persistence failures:
- `DomainValidationError`: invalid title/description/date, immutable-ID violation, duplicate rule, or merge limit. Carries a field and actionable message where applicable.
- `StorageError`: access denied, quota exceeded, or read/write operation failure. Preserve form values and existing DOM state; clearly say the task could not be saved and give the reason when known.
- `StorageCorruptionError`: malformed envelope, invalid record, or unsupported version. Do not silently overwrite or delete it.

First run with no key returns an empty array and displays “No tasks”. Invalid persisted records are rejected at initial load. If corruption is discovered in in-memory data, show extractable values in repairable fields, mark invalid fields with a red outline, and explain the repair needed. A manual “Reset & Start Fresh” action may clear the key only after the user explicitly presses that button; never clear or replace corrupted data automatically. An unreadable raw JSON blob cannot be edited field-by-field, so explain that reset is a user-chosen recovery option.

A failed create/update keeps entered title, description, and dueDates in the form; it does not clear them or optimistically mutate the task DOM. A failed deletion restores affected rows and identifies which tasks failed. Partial batch success is allowed and must identify both the failed operation and the affected task/location.

## 9. Error classes

```javascript
class DomainValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "DomainValidationError";
    this.field = field;
  }
}
class StorageError extends Error {
  constructor(message, originalError = null) {
    super(message);
    this.name = "StorageError";
    this.originalError = originalError;
  }
}
class StorageCorruptionError extends StorageError {
  constructor(message, rawContent = null) {
    super(message);
    this.name = "StorageCorruptionError";
    this.rawContent = rawContent;
  }
}
```
